# 05 复盘

## 最难的问题

1. **确认边界放在哪里**。只靠 prompt 要求“改时间要确认”“不得称已发布”，无法保证模型每次都遵守（本次 live 中模型恰好全部遵守，但换模型或换输入不一定）。最终做法是把边界拆成三层：工具层在写入前拒绝（改时间无待确认项 -> `confirmation_required`，改硬性时间 -> `hard_constraint_violation`），结束时校验结论与账本一致（V1-V8），报告中的事实字段由代码从账本生成。模型仍然自主决定动作，但无法越权写入或虚报结果。
2. **“相同请求只产生一份草稿”与“更换时段后重新提交”同时成立**。若幂等键包含待确认项文字，真实模型两次措辞不同就会产生两份草稿；若只按素材去重，又无法区分换时段的新提交。最终以 `material_id|channel|date|time` 为键：同键原地更新文字，换时段新建并把旧草稿标为 `superseded`，保证任何时刻每个素材只有一份有效草稿。
3. **参考实例的“19:00”不能写死**。替代时间由工具按“小时差升序、同差取晚”计算，并准备第二套排期（17/18/19 均被占）验证会得出 20:00。

## 下一步

- 实现确认回写：用户确认后把草稿从 `pending_confirmation` 改为 `ready`，或拒绝后释放时段。
- 支持跨日期 / 跨渠道的替代方案（需用户先授权放宽硬性要求）。
- 规则从子串匹配升级为可配置的规则引擎或语义审核，并区分渠道规则。
- 草稿存储换成带事务的数据库，支持并发。
- 用更多真实模型对比 live 表现，统计各验收点的通过率。

## 学习收获

1. **Agent 的可靠性主要来自工程边界，而不是 prompt**。prompt 决定模型“倾向于”怎么做，工具层校验、结束时的一致性检查、由账本生成报告，才决定系统“最多会错到什么程度”。第一版 live 中模型没有触发任何防线，我仍然保留了它们，因为防线针对的是模型出错的那一次，而不是平均情况。后来的重跑也印证了这一点：模型把 finish 的结果数组写成了字符串，被参数校验拦下后才自行修正。
2. **写代码前把方案审细，回报很高**。三轮方案审查中发现的问题，例如第二套排期会给出 17:00 而不是 20:00、补查结果对规则检查不可见，如果等到实现后才发现，需要改数据、改代码、改测试。在方案阶段发现，只需要改几行描述。把预期结果写到具体的草稿 ID 和分组，也让 Mock 测试可以逐项断言。
3. **离线 Mock 和真实模型要分开看**。Mock 结果确定，适合做回归测试；真实模型会走出 Mock 没写的策略，例如第一版 live 08 在保存持续失败后判“待确认”并放弃建议时间，模型还会在同一轮并行调用多个工具。评估时我把两者分开列，并且不把 Mock 的结果当作模型能力的证据。
4. **幂等要从“用户感知的同一请求”来定义**。一开始容易想到“内容完全相同才算重复”，但对真实模型来说，同一个请求每次的措辞都会不同。所以幂等键应该取业务上的唯一性（素材加时段），可变的文字在原草稿上更新。
5. **用对比实验补 prompt 的规则空白，而不是凭感觉改**。live 与 Mock 在“保存持续失败”时的结论不一致，暴露出 prompt 没有规定这种情况怎么判。我先保留改动前的记录，再改 prompt，在同一模型、同一用例上重跑对比，改动后两者结论一致，建议时间也得以保留。样本只有各 1 次，所以结论只写到“这次生效”，没有夸大为“稳定生效”。
6. **工程细节同样影响交付**：Windows PowerShell 的编码会让测试结果出现乱码，git 默认不走系统代理，临时目录路径会暴露本机用户名。这些都在提交前逐一处理了。
