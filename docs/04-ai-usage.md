# 04 AI 使用说明

## 使用的 AI 工具

- Cursor（Agent 模式，Claude 模型）：方案起草、代码与测试编写、运行与文档整理
- 阿里云百炼 `qwen3.8-omni-flash`：项目运行时的决策模型（live 运行），不参与开发

## 分工概览

我的工作方式是“我定方向和验收标准、AI 写实现、我通过追问和复查把关质量”。代码与文档初稿由 AI 生成；选题、技术选型、方案审查、完成度核查、模型接入和交付决策由我完成。下面分别说明。

## AI 辅助的范围

| 环节 | AI 产出 | 说明 |
|---|---|---|
| 方案 | 实现方案初稿及每轮修订 | 每轮修订由我提出的审查要求触发，见“个人修改” |
| 代码 | `src/`、`scripts/`、`tests/` 全部代码 | 原生 ReAct 循环、工具、校验、Mock、CLI |
| 数据 | `data/`、`examples/inputs/` | 合成数据，按方案中的数值生成 |
| 运行 | Mock 与 live 运行、结果整理 | live 使用我提供的模型配置 |
| 文档 | README 与 `docs/01-05` | 依据开发过程记录起草，由我审阅 |

## 个人修改

我没有逐行手写代码，我的修改集中在**方向决策**和**通过审查推动的方案与实现修正**：

1. **选题与技术选型**。从四道题中选择“素材审核与发布排期”；在 AI 给出的选项中确定 Python 原生实现 ReAct 循环（不引入框架）、OpenAI 兼容接口（可切换 DeepSeek / 通义等）、CLI 运行。理由：题目说明“框架名称不加分，能解释取舍才有价值”，原生实现每一处逻辑都能讲清楚，也最容易离线复现。

2. **三轮方案审查，在写代码前改掉了一批问题**。我先后要求 AI 检查方案“是否存在不合理、冗余、过度设计、潜在问题”“是否足够细致、避免实现偏差”，并在此基础上“再检查一遍”。这三轮审查带来的主要修改：
   - **删掉过度设计**：去掉单独的 `request_confirmation` 工具，改为“保存时附待确认项”；规则从 5 条精简为有用例覆盖的 3 条；输入文件从 9 个精简为 5 个，用 CLI 参数组合出 10 次运行。
   - **报告改由代码组装**：模型只给结论、建议时间和理由，风险、草稿状态、发布状态都从工具账本生成。这样模型即使在文字里谎称“保存成功”，也进不了报告。
   - **修正会导致验收失败的问题**：
     - 补查结果原本对规则检查不可见，会导致“补查成功”这条路走不通；
     - 第二套排期里 17:00 原本是空的，按排序规则会给出 17:00，而不是预期的 20:00；
     - 幂等键原本包含待确认项文字，真实模型两次措辞不同就会生成两份草稿。
   - **简化硬性要求的建模**：渠道和日期固定为硬性要求，时间是否可改只用一个开关 `time_hard` 控制。
   - **提高兼容性和可复现性**：finish 的参数不再允许为 null，以兼容更多 OpenAI 兼容接口；故障注入只作用于保存工具；草稿 ID 按序号生成；测试结果以 UTF-8 落盘。

3. **实现后逐条对照方案做完成度核查**。我要求 AI 逐条核对方案是否全部完成，因此补上了以下遗漏，测试从 63 个增加到 66 个：
   - 调用不存在的工具时，`reason` 参数会被写进 trace；
   - 保存校验的先后顺序有两处没有测试覆盖；
   - V7 缺少正例；
   - 重复提交后没有断言“草稿只有 1 条”。

4. **接入真实模型并决定交付方式**。我选择并配置了阿里云百炼的 `qwen3.8-omni-flash`。密钥只写在本地 `.env` 中，没有进入对话或仓库。仓库为公开仓库，提交作者使用 GitHub 隐私邮箱。

## 个人验证

- **审查方案与实现汇报**：逐轮阅读 AI 的方案和修订说明，对照题目的“必须验收”和“审核要点”提出复查要求（见上文）。
- **核对运行结果与差异**：阅读 Mock 与 live 的结果汇总。重点确认了以下几点：
  - 参考实例（M01 想要 18:00 但已被占用，建议 19:00 并标为待确认，没有称已发布）在两种模式下都成立；
  - live 08 的结论与 Mock 不同（模型判“待确认”，Mock 判“通过”），但两者都明确报告了保存失败，因此判断为合理的策略差异，不是缺陷，并要求如实写入 `03-evaluation.md`。
- **关注 live 中防线没有被触发**：live 10 次运行里 finish 一次都没被打回，保存也没有被校验拒绝。所以工具层校验和 V1-V8 的有效性要靠 `tests/test_agent_scripted.py` 等测试来证明，这一点已在评估文档中写明。
- **安全检查**：确认 `.env` 在 `.gitignore` 中；推送后在远端查询 `.env` 返回 404；运行记录中的临时目录路径已脱敏为 `<tempdir>`。
- **可复现的验证命令**（不需要模型 Key）：
  ```powershell
  python scripts/run_tests.py                                   # 66 passed
  python -m src.main --request examples/inputs/case02_conflict.json --mock
  python scripts/run_examples.py --mode mock
  ```

## AI 自身的验证与纠错记录

- 所有 Mock 运行结果都与方案中逐条写明的预期对照，一致后才写入 `03-evaluation.md`。
- 写测试时发现一个 V8 用例设计错误：“不会发布成功之外的状态”中，“发布成功”前一个字是“会”，正则会命中，与用例的期望不符。已改为真正属于否定表述的用例，并在已知限制中写明 V8 的误判边界。
- 运行记录中的临时目录绝对路径会暴露本机用户名，已改为 `<tempdir>`。
- 第一次推送 GitHub 时直连超时，排查发现系统代理为 `127.0.0.1:7897`，只在推送命令中临时指定该代理，没有修改全局配置。

## 个人理解

**循环如何工作**。`run_once` 每一步调用一次模型。模型返回要调用的工具和参数，循环执行工具，把结果作为 tool 消息回填，再由模型决定下一步，直到模型单独调用 `finish` 并通过校验。下一步做什么完全由模型根据工具结果决定，例如时段被占用就去选替代时间，字段缺失就去补查，代码不做固定分支。为了防止模型无限循环，设置了模型调用 20 步、工具调用 40 次、finish 打回 2 次三个上限，超过任何一个都返回 `incomplete` 并说明原因。

**为什么由代码组装报告**。题目把“越权发布、虚报保存成功”列为关键缺陷。只靠 prompt 约束模型，不能保证它永远遵守，所以我采用三层防线：
1. 工具层在写入前拒绝越界操作：改了时间却没有待确认项、修改硬性时间、时段冲突；
2. `finish` 提交时检查结论与账本是否一致（V1-V8）；
3. 报告中的事实字段直接从账本生成。

这样模型保留了决策权，但没有改写事实的能力。

**幂等键的取舍**。“相同请求只产生一份草稿”和“换了时段可以重新提交”需要同时成立。如果幂等键包含待确认项文字，模型每次措辞不同就会多出一份草稿；如果只按素材去重，又分辨不出换时段的新提交。所以幂等键取 `素材|渠道|日期|时间`：键相同时在原草稿上更新文字；换了时段就新建草稿，并把旧草稿标为 `superseded`。这样任何时刻每个素材只有一份有效草稿。

**Mock 的边界**。Mock 是规则策略，只能证明循环、工具和防线能跑通，不能证明模型决策得好。能证明模型会根据工具结果调整动作的，是 `examples/runs/live/` 下的真实运行记录。
